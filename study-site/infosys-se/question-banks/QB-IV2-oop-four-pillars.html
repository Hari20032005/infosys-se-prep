QB-IV2 — OOP — The Four Pillars, Overloading vs Overriding

Interview · Tier 1 · 54 questions

Topic file: IV2-oop-four-pillars.md

Adapted from accenture-prep-final/accenture-prep-library/question-banks/QB-T05-D1-oop-four-pillars.md; verified in that library's QA. Questions and answer key are unchanged.

How to use this bank. Attempt every question before opening the key, at the real pace for this section (120 seconds a question). Answer letters are balanced across a–d.

1. [Easy] (D1 — runtime polymorphism)

What is the output of the following Java program?

class Animal { void sound() { System.out.print("generic "); } }
class Dog extends Animal { void sound() { System.out.print("bark "); } }

public class Main {
    public static void main(String[] args) {
        Animal x = new Dog();
        x.sound();
        Animal y = new Animal();
        y.sound();
    }
}

(a) bark generic (b) generic bark (c) bark bark (d) generic generic

1. (a) bark generic x is declared Animal but refers to a Dog, so the overridden Dog.sound() runs; y refers to a plain Animal, so its own version runs. - (d) Assumes the declared (reference) type decides which override runs — that is field/static behaviour, not instance method dispatch. - (b) Swaps the two calls; the first object is a Dog, not an Animal. - (c) Assumes both variables share the same dynamic type; y was created with new Animal().

Statement Reference type Object type Method executed
x.sound() Animal Dog Dog.sound() → "bark "
y.sound() Animal Animal Animal.sound() → "generic "

2. [Easy] (D1 — overloading vs overriding)

Which statement correctly distinguishes overloading from overriding?

(a) Overloading requires an inheritance relationship; overriding does not. (b) Overloading is resolved at runtime; overriding is resolved at compile time. (c) Overloading uses the same method name with different parameter lists in the same class or class hierarchy; overriding redefines an inherited method with the same signature. (d) Overloading can differ from the original method only in return type.

2. (c) Overloading uses the same method name with different parameter lists in the same class or class hierarchy; overriding redefines an inherited method with the same signature. Overloading is compile-time (static) polymorphism keyed on the parameter list; overriding is runtime (dynamic) polymorphism requiring the same signature in a subtype. - (b) Reverses the binding times: overloading is resolved at compile time, overriding at runtime. - (a) Reverses the requirement: overriding needs inheritance, overloading does not. - (d) A return type alone cannot distinguish overloads; Java rejects two methods differing only in return type.

3. [Easy] (D1 — encapsulation)

A class declares all its fields private and exposes only public methods that read or modify them with validation. Which OOP pillar does this primarily demonstrate?

(a) Inheritance (b) Polymorphism (c) Encapsulation (d) Composition

3. (c) Encapsulation Private fields plus controlled public accessors bundle state with the behaviour that guards it, which is encapsulation. - (a) No superclass/subclass relationship is involved. - (b) No method is redefined or resolved dynamically by object type. - (d) Composition is a whole-part object relationship, which this snippet does not show.

5. [Easy] (D3 — abstract class vs interface)

Which statement about Java abstract classes and interfaces is correct?

(a) A class may extend multiple abstract classes but implement only one interface. (b) An interface may declare constructors; an abstract class may not. (c) An abstract class may not contain any concrete (fully implemented) methods. (d) An abstract class may have instance fields and constructors; an interface's fields are implicitly public static final.

5. (d) An abstract class may have instance fields and constructors; an interface's fields are implicitly public static final. An abstract class is a real class and can hold state and constructors; interface fields are constants by definition. - (a) Reverses the rule: a class can implement many interfaces but extend only one class. - (b) Interfaces cannot declare constructors; abstract classes can. - (c) Abstract classes may contain any number of concrete methods.

6. [Easy] (D3 — access modifiers)

Which sequence lists Java access modifiers from MOST restrictive to LEAST restrictive?

(a) private, protected, default (package-private), public (b) default (package-private), private, protected, public (c) protected, private, default (package-private), public (d) private, default (package-private), protected, public

6. (d) private, default (package-private), protected, public private is class-only; package-private adds the package; protected adds subclasses (and same-package access); public is unrestricted. This is strictly increasing visibility. - (a) Places protected below package-private, but protected grants everything package-private grants plus subclass access. - (c) Starts with protected, which is not the most restrictive. - (b) Starts with package-private, which is not the most restrictive.

7. [Medium] (D2 — static method hiding vs overriding)

What is the output?

class Parent {
    static void show() { System.out.print("Parent "); }
    void print() { System.out.print("Pprint "); }
}
class Child extends Parent {
    static void show() { System.out.print("Child "); }
    void print() { System.out.print("Cprint "); }
}
public class Main {
    public static void main(String[] args) {
        Parent p = new Child();
        p.show();
        p.print();
        Child c = new Child();
        c.show();
    }
}

(a) Parent Pprint Child (b) Child Cprint Child (c) Parent Cprint Child (d) Child Pprint Parent

7. (c) Parent Cprint Child static methods are hidden, not overridden, so p.show() is bound by the reference type (Parent) → "Parent ". print() is a normal instance method, so p.print() dispatches to Child → "Cprint ". The second show() call is on a Child reference → "Child ". - (a) Assumes print() also dispatches by reference type. - (b) Assumes static methods are dispatched by object type. - (d) Swaps the two rules: reference type for show(), object type for print().

p.show() static, by reference type Parent Parent
p.print() instance, by object type Child Cprint
c.show() static, by reference type Child Child

9. [Medium] (D2 — virtual vs non-virtual in C++)

What is the output?

#include <iostream>
using namespace std;

class Base {
public:
    void show() { cout << "Base "; }
    virtual void tell() { cout << "BaseTell "; }
};
class Derived : public Base {
public:
    void show() { cout << "Derived "; }
    void tell()  { cout << "DerivedTell "; }
};
int main() {
    Base* b = new Derived();
    b->show();
    b->tell();
}

9. (c) Base DerivedTell show() is non-virtual, so b->show() is bound statically to Base::show → "Base ". tell() is virtual, so b->tell() dispatches to Derived::tell → "DerivedTell ". - (a) Assumes show() is also virtual. - (b) Assumes tell() is not virtual, so no dynamic dispatch occurs. - (d) Reverses the two members: virtual show(), non-virtual tell().

11. [Medium] (D5 — association, aggregation, composition)

Which statement about aggregation and composition is correct?

(a) In composition the part's lifetime is bound to the whole; in aggregation the part can outlive the whole. (b) Association implies ownership; aggregation implies no relationship at all. (c) Composition allows one part to be shared by several wholes simultaneously; aggregation does not. (d) Aggregation is a stronger whole-part relationship than composition because the part is destroyed with the whole.

11. (a) In composition the part's lifetime is bound to the whole; in aggregation the part can outlive the whole. Composition is strong ownership (part destroyed with the whole); aggregation is weak ownership (part exists independently and can be shared). - (d) Inverts the strength of the two relationships. - (b) Both aggregation and association are relationships; aggregation is a specialised association, not the absence of one. - (c) Inverts the sharing property: aggregation permits sharing, composition normally does not.

12. [Medium] (D3 — interface default methods)

What is printed?

interface A { default String who() { return "A"; } }
interface B { default String who() { return "B"; } }
class C implements A, B {
    public String who() { return A.super.who() + B.super.who(); }
}
public class Main {
    public static void main(String[] x) { System.out.print(new C().who()); }
}

(a) BA (b) Runtime exception (ClassCastException) (c) Compile-time error, because C inherits two conflicting default methods (d) AB

12. (d) AB Both A and B declare a default who(), but C explicitly overrides it, resolving the conflict. A.super.who() yields "A" and B.super.who() yields "B", concatenated in that order. - (a) Reverses the concatenation order written in C.who(). - (c) The conflict rule only forces an override when a class inherits two defaults without overriding; C does override. - (b) No cast or runtime failure occurs here.

16. [Hard] (D2 — field hiding vs method dispatch)

19. [Easy] (D1 — abstract class vs interface)

21. [Easy] (D1 — static vs instance members)

Which statement about a static method is true?

(a) It can access instance variables of its own class directly.

(b) It is overridden by a subclass method with a different return type.

(c) It cannot be overloaded.

(d) It can be called using the class name without creating an instance of the class.

21. (c) It can be called using the class name without creating an instance of the class. Static methods belong to the class, not to an object, so no instance is required.

  • (a) A static method has no this, so it cannot touch instance variables directly.
  • (b) Overloading depends only on the parameter signature and applies to static methods too.
  • (d) Static methods are hidden, not overridden, and hiding requires a compatible return type.

(c) C followed by a runtime exception

(d) P

  • (d) Dynamic dispatch applies only to instance methods, not to static methods.
  • (b) It compiles; calling a static method through an instance reference is legal in Java.
  • (c) No exception occurs; the static call is bound to P.f() at compile time.

23. [Medium] (D1 — association vs aggregation vs composition)

An Order object creates its own OrderLine objects inside its constructor, and no other object ever holds a reference to those OrderLine objects. When the Order is discarded, its lines are gone with it. Which relationship is modelled?

(a) Association

(b) Aggregation

(c) Composition

(d) Inheritance

23. (c) Composition The whole creates the parts, owns them, and their lifetime ends with it — the defining traits of composition.

  • (b) Aggregation parts are separate objects referenced from outside and can outlive the whole.
  • (a) Association is a general link with no ownership or lifetime control.
  • (d) Inheritance is an "is-a" relationship, not a whole–part one.

24. [Medium] (D1 — abstract class vs interface)

(b) Shape cannot be instantiated, and a class extending Shape that does not implement area() must itself be declared abstract.

(c) Every subclass of Shape must implement area(), whether or not it is declared abstract.

(d) An anonymous subclass of Shape must override both area() and describe().

24. (d) Shape cannot be instantiated, and a class extending Shape that does not implement area() must itself be declared abstract. An abstract class cannot be instantiated, and any concrete subclass must implement all inherited abstract methods.

  • (a) Concrete methods do not make an abstract class instantiable.

25. [Medium] (D1 — access modifiers and visibility)

25. (d) A protected member is visible in the same package and, from a subclass in another package, only through a reference whose type is that subclass or a subtype of it. This matches the JLS rule for protected access from a subclass in a different package.

26. [Medium] (D1 — association vs aggregation vs composition)

Which statement about whole–part relationships is true?

28. [Easy] (D1 — constructor chaining order)

What does this program print?

    public static void main(String[] args) { new B(); }
}

(a) A5AB (b) ABA5 (c) AA5B (d) A5B
